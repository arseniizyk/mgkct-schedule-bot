# План перехода на монолит и оптимизации mgkct-schedule-bot

## 1. Общая цель
Трансформировать проект из распределенной микросервисной системы (6 Docker-контейнеров: 2x Postgres, NATS, gRPC, Scraper, Tg-bot, Adminer) в **легковесный модульный монолит (Single Go Binary)**, устранить критические ошибки логики и обеспечить возможность развертывания на **100% бесплатном хостинге** (Koyeb / Render / Fly.io / Free VPS).

---

## 2. Стратегия скрапинга: Умный динамический опрос (Smart Event-Driven Polling)

Поскольку расписание на новую неделю выкладывают во второй половине пятницы или утром в субботу, реализуется режим динамического переключения частоты:

### Режимы работы планировщика:
1. **Турбо-режим (Пятница 12:00 — Суббота утро):**
   - Период опроса: **каждые 20–30 секунд** (активный поиск новой недели).
   - Как только зафиксировано появление новой недели:
     - Рассылается уведомление пользователям (строго 1 раз!).
     - Планировщик автоматически **выключает турбо-режим** и возвращается в штатный интервал.
2. **Штатный дневной режим (Будни 08:00 — 22:00):**
   - Период опроса: **1 раз в минуту** (проверка точечных замен и изменений).
3. **Ночной режим (22:00 — 08:00) и Воскресенье:**
   - Период опроса: **раз в 15–30 минут** (для экономии ресурсов сервера и минимизации лишних запросов).

### Параметры конфигурации (`.env`):
- `SCRAPE_INTERVAL=1m` — штатный интервал.
- `SCRAPE_PEAK_INTERVAL=25s` — интервал в турбо-режиме.
- `SCRAPE_NIGHT_INTERVAL=20m` — ночной интервал.

## 3. Архитектурная реорганизация: Переход на монолит

```
Было (6 контейнеров, ~450 МБ RAM):
[tg-bot] <──(gRPC/NATS)──> [scraper] <──(NATS)
   │                           │
   ▼                           ▼
[bot-postgres]          [scraper-postgres]

Станет (1 бинарник / 1 контейнер, ~25 МБ RAM):
┌──────────────────────────────────────────────────────┐
│                    mgkct-bot                         │
│                                                      │
│  ┌────────────────┐            ┌──────────────────┐  │
│  │ Scraper Engine │ ──(Chan)──►│  Telegram Engine │  │
│  └───────┬────────┘            └────────┬─────────┘  │
│          │                              │            │
│          └──────────────┬───────────────┘            │
│                         ▼                            │
│           База данных: SQLite / 1x Postgres          │
└──────────────────────────────────────────────────────┘
```

### 3.1. Ликвидация NATS и gRPC
- **Вместо gRPC:** Прямой вызов методов Go через интерфейсы (`ScheduleService`, `TeacherService`). Устраняются Protobuf-генерация, сетевые сокеты и лишняя сериализация данных.
- **Вместо NATS:** Внутрипроцессные Go-каналы (`chan entities.ScheduleUpdate`) или потокобезопасная шина событий (Event Bus/Observer).

### 3.2. Консолидация базы данных
- Объединение трех таблиц в единую схему:
  - `schedules` (расписание групп)
  - `teacher_schedules` (расписание преподавателей)
  - `users` (пользователи, их выбранная группа/преподаватель и состояние)
- **Вариант хранения:**
  - **Вариант А (Основной, локальный):** **SQLite** (драйвер `modernc.org/sqlite` без CGO) в режиме `WAL`. Идеально для 1 контейнера, 0 сетевых задержек, 0 дополнительных сервисов.
  - **Вариант Б (Облачный):** Единый бесплатный PostgreSQL инстанс (например, Neon.tech / Supabase / Render Postgres).
- Все goose-миграции объединяются в один каталог: `internal/infrastructure/db/migrations`.

### 3.3. Структура проекта
Реорганизация в единый Go-модуль:
```
cmd/bot/main.go               # Единая точка входа
internal/
  app/                        # Инициализация и graceful shutdown
  config/                     # Конфигурация (cleanenv)
  domain/                     # Доменные сущности (Group, Teacher, User)
  service/
    schedule/                 # Бизнес-логика расписания
    scraper/                  # Движок адаптивного парсинга (Smart Polling)
    bot/                      # Логика бота
  infrastructure/
    parser/                   # Парсер HTML (Colly / goquery)
    db/                       # Репозитории и миграции (SQLite / PG)
    telegram/                 # Обработчики telebot, клавиатуры, форматирование
```

## 4. Пошаговые этапы выполнения

### Этап 1. Подготовка единого модуля и объединение БД
1. Инициализировать корневой `go.mod` и объединить зависимости.
2. Создать единую директорию миграций `migrations/*.sql` со всеми тремя таблицами (`schedules`, `teacher_schedules`, `users`).
3. Реализовать универсальный репозиторий (с поддержкой SQLite / Postgres).

### Этап 2. Слияние бизнес-логики и отказ от gRPC/NATS
1. Перенести доменные модели из `proto` в чистые структуры Go (`internal/domain`).
2. Заменить NATS-паблиш на передачу событий в Go-канал `eventCh := make(chan UpdateEvent, 100)`.
3. Соединить обработчики Telegram напрямую со службой расписания без сетевых клиентов.

### Этап 3. Исправление накопленных багов
1. **Устранить шторм уведомлений о новой неделе:**
   - Отправлять событие `NewWeekDetected` ровно **один раз**, а не 50 раз по каждой группе.
   - Убрать `continue`, чтобы обновленное расписание группы не терялось при смене недели.
2. **Безопасная рассылка и защита от бана Telegram (Rate Limiter):**
   - Убрать жесткий таймаут 5 секунд на рассылку.
   - Сделать Worker Pool рассылки с лимитом 25 сообщений в секунду и обработкой HTTP 429 (`Retry-After`).
3. **Исправить Data Race в кэше:**
   - Корректно обернуть доступ к `ss.cache` и мапам хэшей в `RWMutex`.
4. **Исправить навигацию по преподавателям:**
   - В `/teacher` собирать имя через `strings.Join(args, " ")`.
   - В инлайн-кнопках передавать идентификатор преподавателя (или хэш/ID), а не `chatID`.
5. **Исправить `/teachers`:**
   - Использовать разбиение длинного списка преподавателей на сообщения до 4096 символов через `SplitMessage`.
6. **Исправить `ValidateTeacher`:**
   - Если есть точное совпадение (`lower == lowerName`), отдавать приоритет ему, не блокируя выбор из-за частичных совпадений других фамилий.
7. **Оптимизировать состояния пользователей:**
   - Хранить промежуточное состояние (ожидание ввода группы/преподавателя) в `sync.Map` в памяти, а не писать в диск на каждую команду `/`.
8. **Очистить HTML-парсер:**
   - Декодировать HTML entities и удалять вложенные теги из ячеек расписания.

### Этап 4. Реализация умного планировщика (Smart Polling)
1. Реализовать динамический таймер с поддержкой переключения периодов (турбо в Пт-Сб раз в 25 сек -> сброс на 1 мин после выкатки новой недели).
2. Добавить `User-Agent` браузера и сетевой Backoff.

### Этап 5. Docker и бесплатный деплой
1. Написать минимальный `Dockerfile` (образ на `alpine`, размер < 30 МБ).
2. Подготовить конфиги запуска для бесплатного хостинга (Koyeb / Render / Fly.io / VPS).
